# ADR-0016. Пользователи деактивируются, а не удаляются

## Контекст

Администратору нужно уметь закрыть кому-то доступ. Учётная запись пользователя связана с плейлистами,
избранным, историей прослушиваний, событиями воспроизведения, аффинити, профилем вкуса, кэшем
рекомендаций и привязкой Last.fm — и почти все эти связи настроены на `Cascade`.

## Варианты

1. **Физическое удаление** строки `users`.
2. **Мягкое удаление** флагом `IsActive`.
3. **Анонимизация**: удалить личные данные, сохранить обезличенную активность.

## Решение

Вариант **2**. Флаг `IsActive` в
[`User`](../../../backend/src/MusicStreaming.Domain/Entities/User.cs), физического удаления
пользователей в API нет вовсе.

Довод — необратимость. `DELETE FROM users` из-за каскадов уносит **всё, что человек когда-либо
слушал**: плейлисты, лайки, историю, накопленный за годы профиль вкуса. Отменить это нечем — бэкапа
может не быть, а если есть, восстановление из него означает откат всей базы.

При этом задача, которую решает администратор, звучит как «закрыть доступ», а не «стереть следы».
Мягкое отключение решает её полностью.

Вариант 3 не выбран как несоразмерный: у приложения нет обязательств по удалению персональных данных
— это личный сервер с доверенным кругом пользователей.

## Что происходит при деактивации

1. `IsActive = false`;
2. **все refresh-токены отзываются немедленно** (`AdminUserService`), поэтому продлить сессию нельзя;
3. вход блокируется — причём проверка `IsActive` стоит **после** проверки пароля, чтобы ответ не
   выдавал существование учётной записи;
4. `RefreshAsync` тоже проверяет `IsActive` — обновление единственная точка продления сессии.

Текущий access-токен при этом продолжает действовать до истечения срока (минуты). Мгновенно
инвалидировать выданный JWT нельзя по построению — см. [ADR-0013](0013-jwt-in-cookie.md).

## Последствия

**Получаем:**
- Отключение обратимо: снял флаг — человек вернулся вместе со всей своей историей.
- Целостность данных сохраняется: рекомендации и статистика не теряют часть выборки.
- Нет риска каскадного удаления по ошибке.

**Платим:**
- Деактивированные записи накапливаются, имя пользователя остаётся занятым.
- Способа удалить данные пользователя по требованию нет. При необходимости это ручная работа с базой.
- Задержка до нескольких минут между деактивацией и фактической потерей доступа — на время жизни
  access-токена.
- **Учётную запись владельца деактивировать бесполезно**: она восстанавливается на старте, см.
  [ADR-0012](0012-owner-reseeded-on-startup.md).

## Когда пересматривать

Если сервис перестанет быть личным и на него распространятся требования об удалении персональных
данных.
