# ADR-0009. jsonb для значений вместо отдельных таблиц

## Контекст

Три структуры — строки синхронизированного текста, топ исполнителей и жанров в профиле вкуса,
содержимое полки рекомендаций — представляют собой **списки**, принадлежащие одной родительской
записи.

## Варианты

1. **Отдельная таблица** на каждый список, со связью и порядком.
2. **Колонка `jsonb`** с сериализованным списком.
3. **Owned entity collection** средствами EF.

## Решение

**`jsonb`**, через общий конвертер в
[`Configurations/RecommendationConfiguration.cs`](../../../backend/src/MusicStreaming.Infrastructure/Persistence/Configurations/RecommendationConfiguration.cs):

| Тип | Где хранится |
|---|---|
| `IReadOnlyList<LyricLine>` | `track_lyrics.synced` |
| `IReadOnlyList<TasteEntry>` | `user_taste_profiles.top_artists`, `top_genres` |
| `IReadOnlyList<CachedRecommendation>` | `recommendation_cache.payload` |

Критерий, по которому выбран jsonb, один: **эти списки никогда не запрашиваются по отдельности**.
Их не фильтруют, не соединяют и не агрегируют — только читают и записывают целиком вместе с
родителем. Строка синхронизированного текста имеет смысл лишь в составе всего текста; топ-20
исполнителей читается как единое целое; полка рекомендаций отдаётся целиком.

Отдельная таблица под такой доступ означала бы `JOIN` и `ORDER BY position` на каждое чтение — ради
данных, которые всё равно берутся целиком.

## Важная деталь: `ValueComparer`

Конвертер сам по себе недостаточен. EF Core должен уметь понять, изменился ли список, — иначе он
либо шлёт `UPDATE` всегда, либо не шлёт никогда. Поэтому рядом с конвертером объявлен компаратор:

```csharp
public static ValueComparer<IReadOnlyList<T>> Comparer<T>() => new(
    (left, right) => left != null && right != null ? left.SequenceEqual(right) : left == right,
    list => list.Aggregate(0, (hash, item) => HashCode.Combine(hash, item)),
    list => list.ToList());
```

`SequenceEqual` здесь работает корректно **только потому, что все три хранимых типа объявлены как
`record`** — у них структурное равенство. Если кто-то заменит `record CachedRecommendation` на
обычный `class`, сравнение молча станет ссылочным, и изменения полки перестанут сохраняться. Это не
вызовет ни ошибки компиляции, ни исключения — просто данные не обновятся.

## Последствия

**Получаем:**
- Чтение полки — одна строка по первичному ключу, без соединений.
- Схема проще: три таблицы, которых нет.
- Изменение формы значения (новое поле в `TasteEntry`) не требует миграции схемы.

**Платим:**
- По содержимому нельзя искать средствами LINQ. Postgres умеет запрашивать jsonb, но EF-запрос к
  элементу списка здесь не написать.
- Целостность внутри json не гарантируется базой: идентификатор исполнителя в `TopArtists` может
  указывать на удалённого исполнителя. Для профиля вкуса это допустимо — он пересчитывается.
- Обязательное условие «хранимые типы — `record`» держится на дисциплине.

## Когда пересматривать

Если понадобится запрос вида «у кого в топе есть этот исполнитель» — под него нужна нормальная
таблица.
