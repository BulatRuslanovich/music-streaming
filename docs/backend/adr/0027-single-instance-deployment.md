# ADR-0027. Развёртывание в один экземпляр

> **Самая важная запись для того, кто принимает проект.** Она фиксирует границу, за которой
> архитектуру придётся менять, и объясняет, почему нельзя просто добавить реплику.

## Контекст

Приложение — self-hosted сервис для личной библиотеки: владелец, его семья и, может быть, друзья.
Десятки пользователей, один сервер.

## Варианты

1. **Проектировать под горизонтальное масштабирование** с самого начала: общее состояние во внешних
   хранилищах, никаких предположений о количестве процессов.
2. **Один экземпляр**, пользуясь этим где выгодно.
3. **Один экземпляр, но без опоры на это** — состояние всё равно снаружи, «на всякий случай».

## Решение

Вариант **2**, осознанно и с фиксацией последствий.

Предположение «процесс ровно один» использовано в пяти местах, и каждое даёт конкретный выигрыш:

| Место | Что даёт | Что сломается при второй реплике |
|---|---|---|
| `EventIngestQueue` + единственный писатель событий | Watermark по `Sequence` корректен по построению ([ADR-0022](0022-droppable-telemetry.md)) | **Молчаливая потеря событий**: событие с меньшим `Sequence` станет видимым после того, как watermark уже прошёл дальше |
| `PlaybackSessionRegistry` | Освобождение права играть без таймаутов и уборщиков ([ADR-0024](0024-playback-ownership-via-sse.md)) | Музыка играет на двух устройствах: каждая реплика знает только своих |
| Семафор на встроенную генерацию полок в `RecommendationService` | Первый визит не запускает две генерации сразу | Обе реплики вставляют одну и ту же полку, проигравшая падает на первичном ключе — **пустая главная** |
| `IMemoryCache` (полки на 60 с, доли жанров на 5 мин) | Ноль инфраструктуры | Разные ответы с разных реплик |
| `TranscodeQueue`, `RecommendationRefreshQueue` | Простая передача работы фоновым процессам | Работа выполняется дважды или теряется |

Плюс два ограничения из смежных решений: файловое хранилище
([ADR-0017](0017-filesystem-instead-of-s3.md)) и миграции при старте
([ADR-0011](0011-migrate-on-startup.md)).

**Против варианта 1.** Он потребовал бы Redis (кэш, реестр воспроизведения, pub/sub), долговечной
очереди и объектного хранилища — то есть четыре дополнительных контейнера, которые владелец сервера
должен понимать, настраивать, обновлять и бэкапить. Ради нагрузки, которой не существует: несколько
одновременных слушателей.

**Против варианта 3.** Это худшее из двух: сложность горизонтального масштабирования уже оплачена, а
пользы от неё нет.

## Опасность

Ни одно из этих ограничений **не проявляет себя ошибкой**. Запустите вторую реплику — приложение
поднимется, ответит на запросы и пройдёт healthcheck. Ломаться начнёт постепенно и тихо: часть
событий не учтётся, у кого-то главная окажется пустой, музыка иногда заиграет на двух устройствах.

Поэтому ограничение зафиксировано здесь явно, а не оставлено читателю кода.

## Что можно, а что нельзя

**Можно:**
- вертикально масштабировать (больше CPU, RAM, диска);
- вынести Postgres на отдельный хост;
- поставить несколько экземпляров **фронтенда** — он без состояния;
- перезапускать бэкенд когда угодно: всё состояние в памяти эфемерно по смыслу.

**Нельзя:**
- запускать вторую реплику бэкенда;
- запускать `MusicStreaming.Tools.ArtistImages` во время активной загрузки треков (обе стороны
  трогают одни и те же строки исполнителей);
- рассчитывать на нулевой простой при обновлении.

## Когда пересматривать

Если сервису понадобится обслуживать сотни одновременных слушателей или обеспечивать высокую
доступность. Порядок работ тогда:

1. Реестр воспроизведения → Redis с pub/sub.
2. Приём событий → долговечная очередь, watermark по другому принципу (это самое сложное).
3. `IMemoryCache` → распределённый кэш.
4. Файловое хранилище → S3 (новый адаптер `IMusicStorage`).
5. Миграции → отдельный шаг развёртывания.
6. Фоновые процессы → выделить в отдельный процесс, работающий в одном экземпляре.

Пункт 6 стоит рассмотреть первым: он снимает бо́льшую часть ограничений, оставляя веб-часть
безсостоятельной и масштабируемой.
