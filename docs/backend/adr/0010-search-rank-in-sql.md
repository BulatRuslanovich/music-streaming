# ADR-0010. Ранжирование поиска как SQL-функция

## Контекст

Поиск ищет по четырём сущностям — исполнителям, альбомам, трекам и жанрам — и должен выдавать
результаты в осмысленном порядке: точное совпадение выше, чем «где-то внутри».

## Варианты

1. **Ранжировать в C#** после выборки.
2. **Выразить правило LINQ-выражением** и подставлять в каждый из четырёх запросов.
3. **Функция в базе**, вызываемая из LINQ через `HasDbFunction`.
4. **Полнотекстовый поиск Postgres** (`tsvector`) или внешний поисковый движок.

## Решение

Вариант **3**. Функция `search_rank(value text, term text)` создаётся миграцией `InitialSchema`, а в
C# объявлена заглушкой
[`Application/Common/SearchRank.cs`](../../../backend/src/MusicStreaming.Application/Common/SearchRank.cs),
которая при прямом вызове бросает исключение и существует только для того, чтобы её можно было
написать внутри LINQ. Связывает их
[`ApplicationDbContext.OnModelCreating`](../../../backend/src/MusicStreaming.Infrastructure/Persistence/ApplicationDbContext.cs#L48-L50).

Сама функция:

```sql
CREATE OR REPLACE FUNCTION search_rank(value text, term text) RETURNS integer AS $$
    SELECT CASE
        WHEN value = term                              THEN 0  -- точное совпадение
        WHEN starts_with(value, term)                  THEN 1  -- значение начинается с запроса
        WHEN position(' ' || term in ' ' || value) > 0 THEN 2  -- с запроса начинается слово внутри
        WHEN position(term in value) > 0               THEN 3  -- запрос встречается внутри
        ELSE 4                                                 -- совпало смежное поле
    END;
$$ LANGUAGE sql IMMUTABLE STRICT PARALLEL SAFE;
```

**Против варианта 1.** Ранжирование в памяти означает, что из базы нужно вытащить **все** совпадения,
чтобы отсортировать и взять первые двадцать. На большой библиотеке это бессмысленная работа.
В SQL же вызов попадает прямо в `ORDER BY`, и `LIMIT` отсекает лишнее в базе.

**Против варианта 2.** Правило одно, а запросов четыре. Записанное четырьмя выражениями, оно рано
или поздно разойдётся — и поиск начнёт ранжировать альбомы иначе, чем треки, без всякой причины.

**Против варианта 4.** `tsvector` заточен под естественный язык — стемминг, стоп-слова, словоформы.
Названия треков и имена исполнителей — не текст на языке: «AC/DC», «M83», «t.A.T.u.» стемминг только
испортит. Здесь нужен подстрочный поиск, и его обслуживают триграммные индексы.

## Сопутствующее: индексы `pg_trgm`

Той же миграцией создаётся расширение `pg_trgm` и четыре GIN-индекса `gin_trgm_ops` на
нормализованных колонках. Без них незаякоренный `LIKE '%term%'` вырождается в полный проход по
таблице: обычный B-tree такое обслужить не может, а класс операторов в модели EF не выражается —
поэтому это ручной SQL внутри миграции, а не конфигурация сущности.

## Приятное следствие

Сравнение идёт с **уже нормализованными** колонками (см. `Normalize.Key`), поэтому в функции нет ни
приведения регистра, ни `LIKE`. `starts_with` и `position` работают с текстом буквально — а значит
поисковый запрос, содержащий `%` или `_`, ищется как обычный текст, и экранировать в нём нечего.
Целый класс ошибок просто не возникает.

## Последствия

**Получаем:**
- Одно правило ранжирования на все четыре сущности.
- Сортировка и отсечение — в базе.
- Нет проблемы экранирования шаблонов.

**Платим:**
- Логика приложения частично живёт в базе: изменить ранжирование — значит написать миграцию.
- `SearchRank.Of()` нельзя вызвать в тесте напрямую — он бросает исключение. Проверяется только
  интеграционно, в `SearchRelevanceTests`.
- Привязка к PostgreSQL становится жёсткой.

## Когда пересматривать

Если понадобится ранжирование с учётом популярности или персональной истории — правило перестанет
быть чистой функцией от двух строк, и его место изменится.
