# 14. Соглашения

## Настройки сборки

[`backend/Directory.Build.props`](../../backend/Directory.Build.props) — общее для всех проектов:

```xml
<Version>1.1.0</Version>
<TargetFramework>net10.0</TargetFramework>
<Nullable>enable</Nullable>
<ImplicitUsings>enable</ImplicitUsings>
<TreatWarningsAsErrors>false</TreatWarningsAsErrors>
<WarningsAsErrors>nullable</WarningsAsErrors>
<InvariantGlobalization>true</InvariantGlobalization>
```

Два пункта здесь важнее остальных:

**`WarningsAsErrors=nullable`** — предупреждения о nullable **ломают сборку**. Это единственная
категория, возведённая в ошибки, и её нельзя обходить через `!` не думая. `!` уместен там, где вы
знаете больше компилятора (например, `t.Artist!.Name` внутри проекции, которую выполняет SQL) — и
такие места лучше сопровождать комментарием.

**`InvariantGlobalization=true`** — в образе нет ICU, приложение **не знает часовых поясов**. Отсюда
`AT TIME ZONE` в статистике и `StringComparer.Ordinal` вместо культурных сравнений. Не пытайтесь
форматировать даты «по-местному» на сервере.

`Version` правится только скриптом релиза ([`13-operations.md`](13-operations.md)).

## Стиль кода

[`backend/.editorconfig`](../../backend/.editorconfig): UTF-8, LF, финальный перевод строки, без
концевых пробелов, отступ 4 пробела в C# и 2 — в `csproj`/`json`/`yml`. Скобки — по стилю Allman
(`csharp_new_line_before_open_brace = all`), системные `using` первыми, без `this.`.

Наблюдаемые в коде соглашения, которых нет в `.editorconfig`, но которых стоит держаться:

- **Первичные конструкторы** для сервисов и контроллеров — так написано всё:
  ```csharp
  public class CatalogService(IApplicationDbContext db, ICurrentUser currentUser)
  ```
- **`sealed`** там, где наследование не предполагается (`PlaybackSessionRegistry`, `RecommendationMetrics`).
- **`record`** для DTO и значений. Для типов, лежащих в jsonb, это **обязательно** —
  [ADR-0009](adr/0009-jsonb-for-value-objects.md).
- **Выражение-тело** для однострочных методов и действий контроллера.
- **Константы вместо магических чисел**, с именем, объясняющим смысл: `MinimumShelfSize`,
  `TagConflictAttempts`, `ReuseGrace`.
- **Строки, которые знают двое, — в константу.** `RequestPipelineSetup.HealthPath`,
  `MetricsSetup.ScrapePath`, `AuthCookies.AccessTokenCookie`, `ShelfKeys.*`.
- **Разделители в длинных файлах** — `// ── Название ────` (используется в тестах и в
  `RecommendationOptions`).

Форматирование проверяет CI (`dotnet format --verify-no-changes`), поэтому:

```bash
cd backend && dotnet format
```

перед каждым коммитом. Это самая частая причина красной сборки.

## Комментарии

Здесь у проекта есть **своя, ясно выраженная культура**, и её нужно поддержать — именно она делает
код передаваемым.

### Правила

**1. Комментарии на русском.** Весь существующий код таков; смешение языков хуже любого выбора.

**2. Объясняем «почему», а не «что».** Сигнатура и так видна. Комментарий нужен там, где решение
неочевидно.

Плохо:

```csharp
/// <summary>Возвращает трек по идентификатору.</summary>
public async Task<TrackDto> GetTrackAsync(Guid id, CancellationToken ct)
```

Хорошо:

```csharp
/// <summary>
/// Текст трека. 204, когда текста нет: его отсутствие — обычное дело, а не ошибка, и клиент
/// не должен показывать из-за этого ни одной тревожной надписи.
/// </summary>
```

**3. Называем отвергнутую альтернативу.** Самые ценные комментарии в проекте объясняют, почему
**не** сделано очевидное:

```csharp
// Обычный словарь под замком, а не ConcurrentDictionary: обе операции читают прежнее значение и
// тут же его заменяют, а атомарного «отдай прежнее и положи новое» у ConcurrentDictionary нет —
// AddOrUpdate возвращает как раз новое.
```

**4. Описываем последствие ошибки.** Если код защищает от чего-то, скажите, от чего:

```csharp
// Без этого его исполнитель, альбом и сам трек уехали бы в базу вместе со следующим файлом —
// причём трек ссылался бы на аудиофайл, который к тому моменту уже удалён.
```

**5. `<para>` для второго абзаца.** Первое предложение `<summary>` — краткая суть, детали — отдельным
абзацем. Так короткая версия остаётся читаемой во всплывающей подсказке IDE.

**6. `<param>` там, где имя параметра не всё говорит.**

### Что комментировать обязательно

- любой обход неочевидной проблемы (гонка, ограничение библиотеки, особенность внешнего сервиса);
- нетривиальный индекс — какой запрос он обслуживает;
- значение любой константы, кроме самоочевидных;
- всё, где «правильное» решение было бы другим.

XML-комментарии попадают в схему OpenAPI (`GenerateDocumentationFile` включён), поэтому `<summary>`
контроллера и его действий — это ещё и текст, который увидит потребитель API на `/docs`.

## Куда класть новый код

| Задача | Что и где |
|---|---|
| **Новая ручка** | Действие в существующий контроллер `Api/Controllers/` + метод сервиса `Application/Services/`. Новый контроллер — только под новую предметную область |
| **Новое поле сущности** | Domain → EF-конфигурация → миграция → DTO → **проекция** → тест. Полный список — сквозной пример в [`README.md`](README.md) |
| **Новая внешняя система** | Порт в `Application/Abstractions/` + адаптер в `Infrastructure/<Папка>/` + регистрация. Даже если реализация в три строки |
| **Новый фоновый процесс** | `BackgroundService` в `Infrastructure/`, `AddHostedService` в `DependencyInjection`. Учтите ограничение одного экземпляра ([ADR-0027](adr/0027-single-instance-deployment.md)) |
| **Новая настройка** | Свойство в `Application/Options/` + **правило валидации** + `appsettings.json` + `.env.example` + таблица в [`11-configuration.md`](11-configuration.md) |
| **Правило скоринга** | `Application/Recommendations/Scoring/` — чистая функция, обязательно с юнит-тестом |
| **Общий хелпер** | `Application/Common/` — статический класс, без состояния |
| **Значение перечисления** | Только **дописать в конец** и никогда не переименовывать |

### Чего делать не нужно

- **Не добавляйте пакеты в `MusicStreaming.Domain`** — его независимость и есть граница архитектуры.
- **Не обращайтесь к `HttpContext` из сервисов** — есть `ICurrentUser`.
- **Не возвращайте коды состояния из сервисов** — бросайте `AppException`
  ([ADR-0005](adr/0005-exceptions-instead-of-result.md)).
- **Не пишите логику в контроллер.** Если там появился `if` — она не на своём месте.
- **Не поднимайте сущность целиком ради трёх полей** — используйте проекцию.
- **Не заводите новую таблицу под исходящую доставку** — есть outbox
  ([ADR-0023](adr/0023-generic-outbox.md)).
- **Не полагайтесь на часовые пояса в C#** — их в образе нет.

## Чек-лист PR

Перед отправкой:

- [ ] `cd backend && dotnet build MusicStreaming.slnx -c Release` — без предупреждений;
- [ ] `dotnet format` — прогнан;
- [ ] `dotnet test MusicStreaming.slnx -c Release` — зелёный, **и Docker при этом запущен** (иначе
      интеграционные тесты просто пропущены);
- [ ] новое поведение покрыто тестом;
- [ ] новая настройка провалидирована на старте и попала в `.env.example`;
- [ ] неочевидные решения прокомментированы, с указанием отвергнутой альтернативы;
- [ ] миграция прочитана глазами (EF любит предложить пересоздать индекс);
- [ ] затронутая глава документации обновлена;
- [ ] если изменилось **решение**, а не реализация, — заведена новая запись в [`adr/`](adr/).

## Когда документация расходится с кодом

**Прав код.** Расхождение чинится в том же PR, что и изменение.

- Изменили поведение, описанное в главе → правите главу.
- Изменили решение, зафиксированное в ADR → **не переписываете** старую запись, а добавляете новую со
  ссылкой «Заменяет NNNN» и помечаете старую как заменённую.

Смысл второго правила в том, что ценность архива — в возможности понять, почему когда-то сделали
иначе. Переписанная задним числом запись эту ценность уничтожает.
