# ADR-0025. Лимит загрузки задан в трёх местах

## Контекст

Загрузка аудио — единственная операция, где клиент присылает большой объём данных. Нужен потолок.
На первый взгляд достаточно проверить размер в сервисе.

## Варианты

1. **Одна проверка в сервисе** (`TrackUploadService`).
2. **Проверка в сервисе + лимит Kestrel.**
3. **Три уровня: обратный прокси, сервер, сервис.**

## Решение

Вариант **3**:

| Уровень | Где | Значение |
|---|---|---|
| Обратный прокси | [`deploy/Caddyfile`](../../../deploy/Caddyfile) | `MAX_UPLOAD_BODY_BYTES`, по умолчанию 256 МиБ |
| Сервер | [`Startup/LimitsSetup.cs`](../../../backend/src/MusicStreaming.Api/Startup/LimitsSetup.cs) | `Storage:MaxUploadBytes` + 1 МиБ |
| Сервис | `TrackUploadService` | `Storage:MaxUploadBytes`, 200 МиБ |

### Почему проверки в сервисе недостаточно

Решающий факт: **ASP.NET Core разбирает multipart до входа в действие.** Привязка
`IFormFileCollection` происходит раньше первой строки кода метода, и всё крупнее нескольких десятков
килобайт к этому моменту уже **сброшено во временный файл на диске**.

То есть запрос, который сервис заведомо отвергнет, успевает занять на диске ровно столько, сколько
прислали. Достаточно нескольких параллельных запросов с гигабайтными телами, чтобы забить диск — и
единственное, что этому мешает, находится в `LimitsSetup`, а не в сервисе.

Отсюда правило: **внешний лимит защищает ресурс, внутренний — формирует внятный ответ.** Ни один не
заменяет другой. Внешний срабатывает грубо (обрыв соединения, 413 от Kestrel), внутренний — вежливо,
через `UploadTooLargeException` с сообщением о допустимом размере.

### Почему значения различаются

Лимит должен **расти** от внутреннего к внешнему:

```
сервис (200 МиБ) < Kestrel (200 МиБ + 1 МиБ) < Caddy (256 МиБ)
```

Запас в 1 МиБ на уровне Kestrel — это накладные расходы multipart: границы частей, заголовки, имена
полей. Без него файл **разрешённого** размера не прошёл бы, потому что тело запроса всегда чуть
больше самого файла. Ровно об этом предупреждает комментарий в
[`.env.example`](../../../.env.example): «Второе число — граница тела запроса на обратном прокси;
держите его выше первого».

Это самая частая ошибка настройки: подняли `MAX_UPLOAD_BYTES`, забыли `MAX_UPLOAD_BODY_BYTES` — и
загрузка падает без внятного объяснения.

### Потолок на запрос, а не на файл

`MultipartBodyLengthLimit` ограничивает **весь запрос**. Пакет из нескольких файлов эндпоинт
принимает, но суммарно не больше, чем весит один допустимый файл. Настоящей загрузки это не
касается: клиент шлёт по одному файлу на запрос.

## Последствия

**Получаем:**
- Отвергнутый запрос не занимает диск.
- Пользователь получает внятное сообщение, а не обрыв соединения.
- Прокси отсекает заведомо неподъёмное, не доводя до приложения.

**Платим:**
- **Три места, которые нужно менять согласованно.** Изменение только одного даёт трудно
  диагностируемое поведение.
- Отношение между ними неочевидно и держится на комментариях в `.env.example` и `LimitsSetup`.

## Смежное

`MinRequestBodyDataRate = null` там же отключает требование минимальной скорости передачи: медленный
мобильный интернет не должен обрывать долгую загрузку.

## Когда пересматривать

Если появится загрузка кусками (chunked/resumable) — она снимет необходимость в больших телах
запроса, и все три лимита можно будет опустить.
