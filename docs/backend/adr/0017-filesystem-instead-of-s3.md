# ADR-0017. Файловая система вместо S3/MinIO

## Контекст

Приложению нужно хранить аудиофайлы, обложки альбомов, фотографии исполнителей, обложки плейлистов,
перекодированные версии треков и ключи Data Protection.

## Варианты

1. **S3-совместимое хранилище** (MinIO в compose или внешний провайдер).
2. **BLOB в PostgreSQL.**
3. **Локальная файловая система.**

## Решение

Вариант **3**. Порт `IMusicStorage`, реализация
[`FileSystemMusicStorage`](../../../backend/src/MusicStreaming.Infrastructure/Storage/FileSystemMusicStorage.cs),
корень задаётся `Storage:RootPath` (в Docker — `/storage`, том с хоста).

Раскладка:

```
storage/
├── music/{xx}/{yy}/{uuid}{ext}   аудио, двухуровневый разброс
├── covers/                        обложки альбомов (webp, несколько размеров)
├── artists/                       фотографии исполнителей
├── playlists/                     обложки плейлистов
├── transcodes/                    кэш перекодирования
└── .dataprotection/               ключи шифрования
```

**Против варианта 1.** MinIO — это ещё один контейнер, ещё один набор учётных данных, ещё один том и
ещё одна вещь, которую владелец сервера должен понимать при установке и не забыть при бэкапе.
Взамен он не даёт ничего: приложение работает в один экземпляр
([ADR-0027](0027-single-instance-deployment.md)), общего доступа нескольких узлов не требуется, а
раздачу файлов клиентам делает сам бэкенд, потому что она требует авторизации.

Главное: **при файловой системе бэкап музыки — это `rsync` каталога**. Владелец может открыть его в
файловом менеджере, скопировать на внешний диск, проверить глазами. Для self-hosted это весомее любых
архитектурных достоинств объектного хранилища.

**Против варианта 2.** Аудио в базе раздувает её на порядки, ломает потоковую отдачу по диапазонам и
делает бэкап неподъёмным.

## Ключевые детали реализации

**Двухуровневый разброс `{xx}/{yy}`** — по последним байтам UUIDv7, которые случайны
([ADR-0008](0008-uuid-v7-identifiers.md)). Без него все файлы легли бы в один каталог, а
десятки тысяч записей в одном каталоге замедляют работу файловой системы.

**`ResolveWithinRoot`** — единственная точка вычисления абсолютного пути. Отвергает абсолютные пути,
двоеточия и всё, что выводит за пределы корня, бросая `UnauthorizedAccessException` (middleware
превращает его в 403 и пишет `Error`). Плюс отдельная проверка допустимого расширения. Дублирование
здесь намеренное: путь строится из данных, пришедших извне, и одной проверки для этого мало.

**Хеш считается на лету.** SHA-256 содержимого вычисляется тем же проходом, что и запись на диск, —
файл не читается дважды. Именно этот хеш обеспечивает уникальность трека и служит ключом кэша
перекодирования и ETag.

## Последствия

**Получаем:**
- Ноль дополнительной инфраструктуры.
- Бэкап — копирование каталога.
- Отдача файла — обычный `FileStream`, потоковая, с поддержкой диапазонов.

**Платим:**
- Горизонтальное масштабирование невозможно без общей файловой системы.
- Ответственность за права доступа и место на диске — на владельце сервера. Контейнер работает от
  uid 1001, поэтому том должен принадлежать `PUID`/`PGID` из `.env`; за этим следит одноразовый
  сервис `storage-init` в compose.
- Атомарность «файл + строка в базе» не гарантируется. Учтено там, где это важно: загрузка
  откатывает незакоммиченные сущности через `ChangeTracker`, а перекодирование пишет во временный
  `.part` и переименовывает атомарно.

## Когда пересматривать

При переходе на несколько экземпляров или на развёртывание, где локальный диск эфемерен
(Kubernetes без постоянного тома).

Порт `IMusicStorage` для этого и существует, но **одним новым адаптером дело не обойдётся**. Половина
порта — `SaveTrackAsync`, `SaveCoverAsync`, `Delete*` — переносится честно. Вторая половина опирается
на локальный путь по самому своему смыслу, и вместе с ней придётся трогать вызывающий код:

| Что | Почему не переносится сам |
|---|---|
| `ResolveExisting` / `ResolveForWrite` | Возвращают абсолютный путь на диске. `TranscodeWorker` отдаёт его ffmpeg, который читает и пишет локальные файлы: понадобится «скачать во временный файл → перекодировать → залить обратно», то есть временный диск нужен всё равно |
| `OpenRead` при отдаче аудио | Диапазоны (`enableRangeProcessing`) нарезает `Seek` по потоку. Поток объектного хранилища перемотку не умеет: либо объект буферизуется целиком, либо заголовок `Range` разбирается вручную и превращается в range-запрос — а это изменение сигнатуры порта |
| Разбор загруженного файла | `AudioUpload.SniffContainer` и TagLib читают файл по пути, уже после сохранения |
| Ключи Data Protection | `PersistKeysToFileSystem` в `LimitsSetup`; для объектного хранилища нужен свой `IXmlRepository` |

Отдельно стоит помнить, что файлы отдаёт бэкенд, потому что отдача требует авторизации. Объектное
хранилище добавит сетевой перенос на весь трафик, а обойти это можно только предподписанными
ссылками — то есть заменой модели доступа на URL-возможности, которые утекают в логи и историю
браузера.
