# ADR-0013. JWT в HttpOnly-cookie наравне с заголовком

## Контекст

Клиент — веб-приложение на Next.js. Ему нужно аутентифицировать запросы к API, включая те, которые
браузер выполняет **сам, без участия JavaScript**: `<audio src="/api/tracks/{id}/stream">`,
`<img src="/api/albums/{id}/cover">`, скачивание файла по ссылке.

## Варианты

1. **Только заголовок `Authorization`**, токен в памяти или в `localStorage`.
2. **Только cookie-сессии** (классические, серверные).
3. **JWT, принимаемый и из заголовка, и из HttpOnly-cookie.**

## Решение

Вариант **3**. Схема остаётся JWT Bearer, но
[`AuthenticationSetup`](../../../backend/src/MusicStreaming.Api/Startup/AuthenticationSetup.cs)
добавляет обработчик `OnMessageReceived`, который при отсутствии заголовка берёт токен из cookie
`ms_access`. Политика cookie — в
[`Api/Auth/AuthCookies.cs`](../../../backend/src/MusicStreaming.Api/Auth/AuthCookies.cs).

**Против варианта 1 — решающий довод.** Тег `<audio>` не позволяет задать заголовок. Обойти это можно
только двумя способами, и оба плохи:

- отдавать токен параметром строки запроса — он попадёт в логи прокси, в историю браузера и в
  `Referer`;
- качать аудио через `fetch` в blob — то есть загружать трек целиком в память перед началом
  воспроизведения, теряя и потоковость, и перемотку по диапазонам.

Cookie решает это бесплатно: браузер отправляет её со всеми подзапросами сам.

**Против варианта 2.** Серверные сессии требуют общего хранилища состояния и лишают возможности
проверять токен без обращения к базе.

Хранение в `localStorage` в варианте 1 отдельно плохо тем, что делает токен доступным любому
JavaScript на странице. `HttpOnly` это закрывает.

## Сопутствующие решения

- **`SameSite=Lax`** — защита от CSRF. Изменяющие запросы (`POST`, `PUT`, `DELETE`) с чужого сайта
  cookie не получат. Межсайтовых сценариев у приложения нет.
- **Refresh-cookie ограничена путём `/api/auth`** — она не отправляется ни с одним обычным запросом,
  то есть не «светится» на каждом обращении к API.
- **`Secure` всегда, кроме Development поверх http** — иначе локальная разработка без TLS
  сломалась бы.
- **Заголовок продолжает работать.** Это оставляет дверь открытой для клиентов, которым cookie
  неудобны, и позволяет пользоваться страницей `/docs`: Scalar шлёт `Authorization`, но после
  обычного входа туда же приходит и cookie.

## Последствия

**Получаем:**
- Потоковое аудио и изображения работают штатными средствами браузера.
- Токен недоступен JavaScript.
- Проверка токена не требует обращения к базе.

**Платим:**
- Два пути получения токена — два места, где можно ошибиться при изменении логики аутентификации.
- Cookie требует внимания к CSRF (закрыто `SameSite=Lax`).
- Тесты обязаны работать по `https://localhost` и с включённой обработкой cookie, иначе `Secure`-cookie
  молча не сохранится — это учтено в `RecommendationApiFixture`, см.
  [`12-testing.md`](../12-testing.md).
- Отозвать выданный access-токен досрочно нельзя: он действует до истечения срока. Поэтому срок
  короткий, а отзыв реализован на уровне refresh-токенов
  ([ADR-0014](0014-refresh-token-rotation.md)).

## Когда пересматривать

Если появится сторонний клиент, работающий не из браузера, — для него достаточно уже существующего
пути через заголовок.
