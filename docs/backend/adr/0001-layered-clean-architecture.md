# ADR-0001. Четыре слоя, а не вертикальные срезы

## Контекст

Приложение нужно было разложить так, чтобы бизнес-правила не зависели от того, что снаружи —
PostgreSQL, файловая система, ffmpeg, HTTP. При этом разработчик у проекта один, и цена «правильной»
структуры не должна превышать пользу от неё.

## Варианты

1. **Классические слои (Clean Architecture).** Domain → Application → Infrastructure → Api, зависимости
   строго внутрь.
2. **Вертикальные срезы (Vertical Slice).** Папка на функцию, внутри — всё: запрос, обработчик,
   валидация, доступ к данным.
3. **Без выраженной структуры.** Один проект, папки по типу файлов.

## Решение

Выбраны **классические слои** — четыре проекта со строгим направлением ссылок.

Основание — характер предметной области. Функции здесь **не изолированы**: каталог, загрузка, поиск,
рекомендации и статистика работают с одними и теми же треками, исполнителями и альбомами. При
вертикальных срезах общая модель либо расползлась бы по срезам копиями, либо всё равно потребовала бы
общего слоя — то есть тех же самых слоёв, только с лишней прослойкой.

Вторая причина — проверяемость границы. Отсутствие пакетов в
[`MusicStreaming.Domain.csproj`](../../../backend/src/MusicStreaming.Domain/MusicStreaming.Domain.csproj)
— это факт, который видно в одну строку и который невозможно нарушить незаметно. У вертикальных
срезов дисциплина держится только на договорённости.

## Последствия

**Получаем:**
- Границы проверяются компилятором, а не ревью.
- Заменяемость внешнего мира: чтобы уйти с файловой системы на S3, достаточно нового адаптера
  `IMusicStorage`.
- Юнит-тесты движка рекомендаций не требуют ни базы, ни веб-хоста — вся математика в
  `Recommendations/Scoring/` чистая.

**Платим:**
- Одна функция размазана по 3–4 файлам в разных проектах. Добавление поля трогает Domain, EF-конфигурацию,
  DTO и проекцию — см. сквозной пример в [`README.md`](../README.md).
- Слой Domain получился анемичным: сущности почти без поведения, логика в сервисах Application. Это
  расхождение с DDD осознанное — при таком размере домена богатая модель не окупается.

## Когда пересматривать

Если появится подсистема, у которой **своя** модель данных и почти нет пересечений с каталогом
(например, биллинг или социальные функции) — её разумно вынести отдельным вертикальным срезом или
отдельным сервисом, не растягивая на неё общие слои.
