# ADR-0011. Миграции применяются при старте приложения

## Контекст

Схему базы нужно приводить в актуальное состояние при развёртывании. Развёртывание здесь — это
`docker compose up -d` на собственном сервере, выполняемый человеком, у которого может не быть ни
.NET SDK, ни исходников.

## Варианты

1. **Отдельный шаг**: `dotnet ef database update` перед запуском.
2. **Init-контейнер** в compose, применяющий миграции до старта приложения.
3. **Приложение мигрирует само** при старте.

## Решение

Вариант **3**.
[`DatabaseInitializer`](../../../backend/src/MusicStreaming.Infrastructure/Persistence/DatabaseInitializer.cs)
вызывается из `Program.cs` в отдельном scope перед `app.Run()`.

Основание — модель распространения. Это self-hosted приложение, которое ставят по инструкции
«скопируйте `.env.example`, заполните, запустите compose». Любой дополнительный шаг здесь — шаг,
который забудут, и приложение стартует на устаревшей схеме. Вариант 2 решал бы это, но потребовал бы
собирать и держать второй образ ради одной команды.

### Устойчивость к неготовой базе

Postgres в compose стартует одновременно с приложением, и `depends_on` с healthcheck не всегда
достаточно. Поэтому миграция обёрнута в цикл: до 12 попыток с нарастающей паузой (не более 5 секунд),
после чего последняя попытка выполняется уже без перехвата — чтобы упасть с настоящей ошибкой, а не
с обобщённой.

```csharp
catch (Exception ex) when (attempt < maxAttempts)
{
    var delay = TimeSpan.FromSeconds(Math.Min(5, attempt));
    logger.LogWarning("Database not ready (attempt {Attempt}/{Max}) …");
    await Task.Delay(delay, ct);
}
```

## Последствия

**Получаем:**
- Развёртывание — одна команда, забыть шаг невозможно.
- Приложение переживает запуск раньше базы.
- Схема и код всегда согласованы: они выкатываются одним образом.

**Платим:**
- **Два экземпляра приложения одновременно мигрировать не могут.** EF берёт блокировку, так что
  повреждения не будет, но старт второго экземпляра затянется или упадёт. Для этого приложения
  ограничение неактуально — оно и так рассчитано на один экземпляр
  ([ADR-0027](0027-single-instance-deployment.md)).
- Неудачная миграция роняет приложение целиком.
- Откат не автоматизирован: `Down` в миграциях написан, но выполнять его нужно руками.
- Долгая миграция задерживает старт, а healthcheck в это время не отвечает.

## Когда пересматривать

При переходе на несколько реплик или на схему развёртывания с нулевым простоем — тогда миграции
должны стать отдельным управляемым шагом.
