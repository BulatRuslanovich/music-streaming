# ADR-0014. Ротация refresh-токенов с обнаружением повторного использования

## Контекст

Access-токен живёт минуты и не отзывается досрочно. Долгоживущий refresh-токен — это то, что
фактически удерживает сессию, и то, кража чего опаснее всего.

Самый тонкий код в репозитории:
[`AuthService.RefreshAsync`](../../../backend/src/MusicStreaming.Application/Services/AuthService.cs#L43-L107).
Разобрать его стоит целиком.

## Варианты

1. **Долгоживущий неизменный токен.** Обновление не меняет refresh-токен.
2. **Ротация без обнаружения.** Каждое обновление выдаёт новый токен, старый отзывается.
3. **Ротация с обнаружением повторного использования.** Предъявление отозванного токена гасит всю
   цепочку сессий.

## Решение

Вариант **3**, с одной существенной поправкой — окном на гонку.

### Базовая механика

- Токен хранится **хешем**: утечка дампа базы не даёт возможности войти.
- Каждое обновление отзывает предъявленный токен (`RevokedAt = now`) и выдаёт новый.
- Отозванные записи не удаляются сразу — именно они позволяют заметить повторное использование.
  Чистятся через сутки (`PruneExpiredTokensAsync`).

### Проблема: две вкладки

Отозванный токен, предъявленный снова, имеет **два** объяснения:

1. **Гонка.** Две вкладки одного браузера одновременно упёрлись в 401 и обе пошли обновляться со
   старой cookie. Вторая пришла с токеном, который первая только что отозвала. Это обычное дело, и
   выкидывать за это из приложения нельзя.
2. **Кража.** Копию цепочки продолжает кто-то ещё.

### Как они различаются

Наивное решение — «если отозван недавно, считать гонкой» — **отменяет защиту само по себе**: вор,
пришедший в течение окна, будет пропущен. Поэтому проверяется не только возраст:

```csharp
var sessionLivesOn = await db.RefreshTokens.AnyAsync(
    t => t.UserId == stored.UserId && t.RevokedAt == null && t.ExpiresAt > now, ct);

if (!sessionLivesOn || now - revokedAt > ReuseGrace)
{
    // гасим всю цепочку
}
```

Логика: **отзыв бывает не только ротацией.** Деактивация пользователя, смена пароля и реакция на
кражу гасят *все* токены разом. Различие в том, что́ остаётся после:

| Причина отзыва | Остался ли живой токен | Вывод |
|---|---|---|
| Ротация при обновлении | **Да** — только что выданный | Сессия продолжается → возможна гонка |
| Деактивация / смена пароля / разбор кражи | **Нет** — погашены все | Гонки быть не может → отказ |

Поэтому условие «живой токен существует **и** прошло меньше `ReuseGrace` (20 секунд)» — необходимое
и достаточное описание гонки.

### Что происходит при обнаружении

Отзываются **все** активные токены пользователя. Кто из двоих настоящий владелец — отсюда не видно,
поэтому закрываются оба: войти заново сможет тот, у кого есть **пароль**, а не тот, у кого есть
только токен.

## Смежные решения в том же файле

- **Проверка `IsActive` при обновлении.** Деактивация и так отзывает токены, но обновление —
  единственная точка продления сессии, и проверка здесь означает, что доступ закрывается навсегда,
  как бы токен ни оказался на руках.
- **Timing-safe вход.** Если пользователя нет, пароль всё равно сверяется с `DummyHash` — иначе по
  времени ответа было бы видно, существует ли имя.
- **Проверка `IsActive` **после** пароля** — иначе ответ сообщал бы о существовании учётной записи
  любому, кто угадал имя.
- **Смена пароля отзывает все сессии и тут же выдаёт новую пару** текущему клиенту: человек,
  меняющий пароль, хочет закрыть чужие устройства, а не своё.

## Последствия

**Получаем:**
- Кража refresh-токена обнаруживается при первом же использовании одной из копий.
- Обычная работа в нескольких вкладках не приводит к разлогиниванию.
- Утечка базы не даёт войти.

**Платим:**
- Самая сложная логика в проекте. Изменять её без понимания таблицы выше нельзя.
- Окно в 20 секунд — компромисс. Вор, укравший токен и использовавший его в те же секунды, пока
  сессия жива, пройдёт. Практически это требует активного перехвата в реальном времени.
- Проверка `sessionLivesOn` — дополнительный запрос на каждое обновление отозванного токена.

## Когда пересматривать

Если появится привязка сессии к устройству — тогда «живой токен» перестанет быть достаточным
признаком гонки и правило придётся уточнять по устройству.
