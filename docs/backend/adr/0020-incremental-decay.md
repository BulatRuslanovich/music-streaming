# ADR-0020. Инкрементальное экспоненциальное затухание

## Контекст

Рекомендации должны опираться на **текущий** вкус, а не на весь архив прослушиваний: то, что человек
слушал два года назад, весит меньше того, что он слушает на этой неделе. Одновременно сырые события
чистятся по сроку хранения ([ADR-0019](0019-three-listening-stores.md)) — то есть данные, по которым
считался вкус, исчезают.

## Варианты

1. **Пересчитывать по сырым событиям** при каждом обращении, взвешивая по давности.
2. **Скользящее окно**: учитывать только последние N дней.
3. **Инкрементальное экспоненциальное затухание**: хранить накопленный вес и момент его актуальности.

## Решение

Вариант **3**. Каждая строка аффинити хранит два поля:

```csharp
/// <summary>Накопленный вес с экспоненциальным затуханием, актуальный на момент DecayAnchor.</summary>
public double DecayedWeight { get; set; }

/// <summary>Момент, на который актуален DecayedWeight.</summary>
public DateTimeOffset DecayAnchor { get; set; }
```

Добавление веса `w` в момент `t`:

```
weight ← weight · 2^(−(t − anchor) / halfLife) + w
anchor ← t
```

Значение в любой последующий момент:

```
value(now) = weight · 2^(−(now − anchor) / halfLife)
```

Периоды полураспада настраиваются раздельно: `TrackHalfLifeDays` = 45, `ArtistHalfLifeDays` = 90,
`GenreHalfLifeDays` = 90. Интерес к конкретному треку остывает вдвое быстрее, чем к исполнителю, — и
это верно по смыслу: треки приедаются, исполнители нет.

**Против варианта 1.** Стоимость растёт с историей пользователя: чем дольше он пользуется сервисом,
тем медленнее работают его рекомендации. И это невозможно после чистки событий — данных просто нет.

**Против варианта 2.** Окно даёт обрыв: трек, выпавший за границу, теряет вес мгновенно и целиком.
Экспоненциальное затухание непрерывно.

## Ключевое свойство

**Роллап стоит O(1) на событие, а сырые события можно удалять.** Накопленный вкус живёт в
`DecayedWeight`, и после удаления событий он не меняется. Именно это делает совместимыми
[ADR-0019](0019-three-listening-stores.md) (события чистятся через 180 дней) и требование «помнить
вкус годами».

Общая часть вынесена в интерфейс `IDecayingAffinity` — у исполнителя и жанра обновление совпадает
дословно. Трек в интерфейс намеренно не входит: у `UserTrackAffinity` вдвое больше счётчиков
(`ReplayCount`, `QueueAdds`, `CompletionSum`, …), и его обновление действительно другое.

Сама математика — в
[`Recommendations/Scoring/AffinityMath.cs`](../../../backend/src/MusicStreaming.Application/Recommendations/Scoring/AffinityMath.cs)
и `RecencyDecay.cs`, обе покрыты юнит-тестами: это чистые функции, для их проверки не нужна ни база,
ни хост.

## Последствия

**Получаем:**
- Постоянная стоимость обновления, независимая от объёма истории.
- Вкус переживает чистку событий.
- Плавное, а не ступенчатое устаревание.
- Настраиваемая скорость забывания на каждом уровне.

**Платим:**
- **Изменение `halfLife` не пересчитывает уже накопленные веса** — они были свёрнуты по старому
  правилу. После правки настройки система придёт к новому поведению постепенно, а не сразу.
- Значение бессмысленно читать без `DecayAnchor`: `DecayedWeight` сам по себе — не «текущий
  интерес», а его значение на момент якоря. Отдельно хранится `Score` — сжатое в (−1, 1) значение на
  момент последнего роллапа, по которому построен индекс и идёт сортировка.
- Порядок применения событий влияет на результат в пределах ошибки округления `double`.

## Когда пересматривать

Если понадобится «забыть» конкретный период (например, чужой человек слушал с вашего аккаунта) —
инкрементальная схема этого не умеет, потребуется полный пересчёт по сохранённым событиям.
