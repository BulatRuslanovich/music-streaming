# ADR-0003. `IApplicationDbContext` вместо репозиториев и Unit of Work

## Контекст

Слою Application нужен доступ к данным, но он не должен зависеть от конкретной СУБД. Канонический
ответ — репозиторий на агрегат плюс Unit of Work.

## Варианты

1. **Репозитории + Unit of Work.** `ITrackRepository`, `IPlaylistRepository`, … и `IUnitOfWork`.
2. **Обобщённый репозиторий.** `IRepository<T>` с `IQueryable<T>` наружу.
3. **Интерфейс над `DbContext`.** `IApplicationDbContext` с `DbSet<T>` и `SaveChangesAsync`.

## Решение

Выбран **интерфейс над `DbContext`** —
[`IApplicationDbContext`](../../../backend/src/MusicStreaming.Application/Abstractions/IApplicationDbContext.cs).
`DbSet<T>` играет роль репозитория, `SaveChangesAsync()` — роль единицы работы.

**Против варианта 1.** Репозиторий полезен, когда он скрывает способ доступа за осмысленным
доменным методом. Здесь запросы слишком разнообразны: пагинация, фильтры, сортировки, проекции,
условное присоединение избранного. Интерфейс репозитория, который это покрывает, вырождается в
`IQueryable` с лишними шагами — либо обрастает десятками узких методов вида
`GetTracksPagedSortedFilteredWithFavorites(...)`.

**Против варианта 2.** Обобщённый репозиторий, отдающий `IQueryable`, не абстрагирует ровным счётом
ничего: вызывающий всё равно пишет LINQ, который должен уметь транслировать конкретный провайдер.
Это та же протечка, но замаскированная.

**За вариант 3.** Он честен: протечка признана и ограничена одним файлом, в котором каждая опасная
часть снабжена комментарием. Тестируемость при этом не страдает — интеграционные тесты работают на
настоящем Postgres, а не на подменах ([ADR-0026](0026-no-mocks-real-postgres.md)), поэтому
подставлять репозиторий незачем.

## Последствия

**Получаем:**
- Запрос пишется там, где он нужен, и ровно тот, который нужен.
- Проекции уезжают в SQL — из базы не приезжает ничего лишнего.
- Меньше кода: нет ни интерфейсов репозиториев, ни их реализаций, ни регистрации.

**Платим:**
- Слой Application зависит от EF Core — см. [ADR-0004](0004-efcore-in-application-layer.md).
- Ничто не мешает написать в сервисе неэффективный запрос: дисциплина держится на ревью, а не на API.
- Сменить ORM без переписывания всех сервисов невозможно. Для self-hosted приложения, жёстко
  завязанного на возможности PostgreSQL (`pg_trgm`, jsonb, `AT TIME ZONE`), это не потеря.

## Когда пересматривать

Если понадобится второй источник данных для тех же сущностей или переход на ORM с другим API.
