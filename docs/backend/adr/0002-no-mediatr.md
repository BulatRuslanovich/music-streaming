# ADR-0002. Без MediatR и CQRS

## Контекст

В .NET-проектах со слоистой архитектурой MediatR — почти рефлекс: контроллер отправляет команду или
запрос, обработчик её выполняет, поведения в конвейере добавляют логирование, валидацию и транзакции.

## Варианты

1. **MediatR с командами и запросами**, поведения для сквозной функциональности.
2. **Прямой вызов сервисов** из контроллеров.
3. **Разделение чтения и записи (CQRS)** с раздельными моделями.

## Решение

Контроллер вызывает метод сервиса **напрямую**. Сервисы зарегистрированы в
[`Application/DependencyInjection.cs`](../../../backend/src/MusicStreaming.Application/DependencyInjection.cs)
как обычные `Scoped`.

Причины:

**Единственное, что даёт MediatR сверх прямого вызова, — это конвейер поведений.** А сквозная
функциональность в этом приложении уже покрыта средствами ASP.NET Core, на уровне выше:
обработка ошибок — middleware, логирование — Serilog, ограничение частоты — `UseRateLimiter`,
авторизация — политики. Заводить второй конвейер внутри первого не за чем.

**Транзакции здесь не нужны как поведение.** Единица работы — один вызов `SaveChangesAsync()`,
и почти всегда он один на сценарий.

**Цена читаемости.** При MediatR переход «от ручки к коду» — это поиск обработчика по типу команды.
При прямом вызове это F12 в IDE. Для проекта, который передаётся другому разработчику, второе
существенно лучше.

CQRS не введён по той же причине: нагрузка на чтение и запись здесь несопоставима по объёму, но
модель у них одна, и раздваивать её незачем. Оптимизация чтения решена иначе — проекциями прямо в
SQL, см. [ADR-0007](0007-manual-projections-instead-of-automapper.md).

## Последствия

**Получаем:**
- Прямая навигация по коду: маршрут → контроллер → сервис → запрос.
- Минус одна зависимость и минус один слой косвенности.
- Явные подписи методов вместо типов-сообщений.

**Платим:**
- Нет единого места, куда можно вклиниться перед каждым сценарием. Если понадобится, например,
  аудит всех изменяющих операций, его придётся либо писать в каждом сервисе, либо вводить
  декораторы DI.
- Некоторые контроллеры получают много зависимостей: у `TracksController` их восемь. Это терпимо,
  но служит сигналом — контроллер стал слишком широким по охвату.

## Когда пересматривать

Если появится настоящая сквозная задача уровня сценария (аудит, многоарендность, кэширование по
типу запроса), которую неудобно решать средствами ASP.NET Core.
