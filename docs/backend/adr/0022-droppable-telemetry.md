# ADR-0022. Телеметрию можно терять, запросы — нет

## Контекст

Плеер шлёт события воспроизведения: старт, пауза, перемотка, скип, завершение, добавление в очередь.
На активном прослушивании это десятки событий в минуту с каждого устройства. Их приём не должен
влиять на воспроизведение.

## Варианты

1. **Писать в базу синхронно** в обработчике запроса.
2. **Неограниченная очередь** в памяти.
3. **Ограниченная очередь, отбрасывающая при переполнении.**
4. **Внешняя очередь** (Redis, RabbitMQ).

## Решение

Вариант **3**.
[`EventIngestQueue`](../../../backend/src/MusicStreaming.Application/Recommendations/EventIngestQueue.cs)
— это `Channel.CreateBounded` на 8192 элемента с `FullMode = DropWrite`:

```csharp
Channel.CreateBounded<PlaybackEvent>(new BoundedChannelOptions(Capacity)
{
    FullMode = BoundedChannelFullMode.DropWrite,
    SingleReader = true,
});
```

Постановка не ждёт: `TryWrite` либо кладёт событие, либо увеличивает счётчик потерь и возвращает
`false`. Счётчик `Dropped` публикуется метрикой — потери видны, а не молчаливы.

Обоснование сформулировано прямо в коде: **«потерянный при всплеске скип стоит доли одного профиля;
остановленный конвейер запросов стоит сессии»**. Это и есть решение — приоритет отдан отзывчивости
воспроизведения, а не полноте телеметрии.

**Против варианта 1.** Обращение к базе в обработчике превращает телеметрию в источник задержки на
пути, который выполняется постоянно.

**Против варианта 2.** Неограниченная очередь при отставании писателя съедает память — то есть
превращает временную проблему в отказ всего процесса.

**Против варианта 4.** Ещё один контейнер и ещё одна точка отказа ради данных, которые допустимо
терять.

## Критично: `SingleReader = true`

Это не оптимизация, а **условие корректности**.

`PlaybackEvent.Sequence` — счётчик базы, служащий watermark для возобновляемого роллапа: профиль
хранит `EventsWatermark`, и следующий проход берёт всё, что больше. Это работает, только если
события становятся видимыми **в порядке возрастания `Sequence`**.

При двух писателях возможна ситуация: транзакция с `Sequence = 100` зафиксировалась раньше
транзакции с `Sequence = 99`. Роллап увидел 100, поднял watermark — и событие 99 не будет учтено
никогда. Потеря молчаливая и невосстановимая.

Поэтому писатель ровно один — `EventIngestWorker`, единственный читатель канала. Батчинг там же:
`ReadBatchAsync` превращает всплеск скипов в одну вставку.

Именно по этой причине **нельзя запускать второй экземпляр приложения** — см.
[ADR-0027](0027-single-instance-deployment.md).

## Почему не `OccurredAt`

Логичнее было бы возобновляться по времени события. Но `OccurredAt` — это **часы клиента**: заснувшая
вкладка присылает пачку событий с временем более старым, чем уже обработанные, и роллап их
пропустил бы. При приёме `OccurredAt` дополнительно зажимается, чтобы сбитые часы устройства не
портили расчёт затухания.

## Последствия

**Получаем:**
- Приём события — запись в память, без обращения к базе.
- Память ограничена по построению.
- Потери измеримы.
- Watermark корректен.

**Платим:**
- События теряются при всплеске. Для рекомендаций это шум, для статистики — небольшая недооценка.
- **Перезапуск теряет всё, что стоит в очереди.** Штатное завершение успевает дописать, аварийное —
  нет.
- Ограничение «один экземпляр» становится жёстким и неочевидным.

## Когда пересматривать

Если события станут источником для чего-то, где потери недопустимы (биллинг, отчётность
правообладателям) — понадобится долговечная очередь и другая схема watermark.
